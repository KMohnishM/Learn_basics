# Module 5: Q&A - Subqueries and CTEs

## 1. What is the difference between IN and EXISTS? When does EXISTS outperform IN?
`IN` compares a single scalar value against a list of values generated by a subquery. It is conceptually evaluated as `value = val1 OR value = val2 OR ...`. `EXISTS` is a boolean operator that evaluates to TRUE as soon as the subquery returns one or more rows.
**Performance:** `EXISTS` generally outperforms `IN` when used with correlated subqueries or against large tables because of "short-circuit evaluation." The database engine stops searching the subquery table the moment it finds the first match. `IN` historically required materializing the entire subquery result set before comparison, though modern optimizers often rewrite `IN` to execute similarly to `EXISTS` (using Semi-Joins). However, `EXISTS` remains strictly predictable.

## 2. Explain the NULL trap with NOT IN. Write an example that demonstrates the problem.
The NULL trap occurs when the subquery passed to a `NOT IN` clause returns a result set containing one or more `NULL` values. Because SQL uses three-valued logic (TRUE, FALSE, UNKNOWN), any comparison with `NULL` (e.g., `id != NULL`) evaluates to `UNKNOWN`. When evaluating `NOT IN`, SQL expands this to a series of `AND` conditions: `id != val1 AND id != val2 AND id != NULL`. Since one condition is `UNKNOWN`, the entire logical chain resolves to `UNKNOWN`. The `WHERE` clause filters out any row that does not explicitly evaluate to `TRUE`, resulting in the query returning zero rows.

```sql
-- If ANY employee lacks a department (dept_id IS NULL), this query returns 0 rows.
SELECT dept_id, dept_name
FROM departments
WHERE dept_id NOT IN (
    SELECT dept_id FROM employees
);
```

## 3. What is a correlated subquery? Give an example and explain why it can be slow.
A correlated subquery is a subquery that references a column from a table in the outer query. It cannot run independently. It can be slow because the database engine must execute the subquery once for every single row evaluated by the outer query (Row-By-Agonizing-Row or RBAR). If the outer query processes 10,000 rows, the subquery executes 10,000 times.

```sql
-- Example: Finding employees earning above their department's average
SELECT e1.name, e1.salary, e1.dept_id
FROM employees e1
WHERE e1.salary > (
    SELECT AVG(salary) 
    FROM employees e2 
    WHERE e2.dept_id = e1.dept_id
);
```

## 4. Write a query using a CTE to find the top customer by revenue in each country.
```sql
WITH customer_revenue AS (
    SELECT 
        c.country, 
        c.customer_id, 
        c.name, 
        SUM(o.amount) AS total_revenue,
        ROW_NUMBER() OVER (PARTITION BY c.country ORDER BY SUM(o.amount) DESC) AS rnk
    FROM customers c
    JOIN orders o ON c.customer_id = o.customer_id
    GROUP BY c.country, c.customer_id, c.name
)
SELECT country, name, total_revenue
FROM customer_revenue
WHERE rnk = 1;
```

## 5. What is the difference between a CTE and a subquery in the FROM clause?
A subquery in the `FROM` clause (derived table) is defined inline where it is used. A Common Table Expression (CTE) is defined at the beginning of the query using the `WITH` clause.
Functionally, they are often identical in execution. However, CTEs offer significant advantages in readability by allowing top-to-bottom procedural reading. Furthermore, CTEs are reusable; a single CTE can be referenced multiple times within the same primary query, whereas a derived table would need to be rewritten entirely.

## 6. Write a recursive CTE to traverse an employee hierarchy and show all levels.
```sql
WITH RECURSIVE employee_hierarchy AS (
    -- Anchor Member: Top-level managers
    SELECT emp_id, name, manager_id, 1 AS level, CAST(name AS VARCHAR) AS path
    FROM employees
    WHERE manager_id IS NULL
    
    UNION ALL
    
    -- Recursive Member: Join to find subordinates
    SELECT e.emp_id, e.name, e.manager_id, eh.level + 1, CAST(eh.path || ' -> ' || e.name AS VARCHAR)
    FROM employees e
    JOIN employee_hierarchy eh ON e.manager_id = eh.emp_id
)
SELECT emp_id, name, level, path
FROM employee_hierarchy
ORDER BY path;
```

## 7. How do you generate a series of dates using a recursive CTE?
You establish an anchor row with the start date, and a recursive query that adds an interval (e.g., 1 day) to the date from the previous iteration, constrained by a `WHERE` clause that dictates the end date.

```sql
WITH RECURSIVE date_series AS (
    SELECT CAST('2023-10-01' AS DATE) AS series_date
    UNION ALL
    SELECT series_date + INTERVAL '1 day'
    FROM date_series
    WHERE series_date < CAST('2023-10-07' AS DATE)
)
SELECT series_date FROM date_series;
```

## 8. Write a query using NOT EXISTS to find products that have never been ordered.
```sql
SELECT p.product_id, p.name
FROM products p
WHERE NOT EXISTS (
    SELECT 1 
    FROM orders o 
    WHERE o.product_id = p.product_id
);
```

## 9. What does ANY/ALL do in a subquery context? Give an example.
`ANY` (or `SOME`) compares a value to the set of values returned by a subquery and evaluates to TRUE if the condition holds true for at least one value in the set. `ALL` evaluates to TRUE only if the condition holds true for every value in the set.

```sql
-- Find products cheaper than ALL products in the 'Premium' category
SELECT name, price
FROM products
WHERE price < ALL (
    SELECT price 
    FROM products 
    WHERE category = 'Premium'
);
```

## 10. When might PostgreSQL materialize a CTE, and why can that be a problem?
Prior to PostgreSQL 12, all CTEs were automatically materialized (executed independently and stored in a temporary tuplestore). From version 12 onwards, non-recursive CTEs used only once are folded into the main query, but they are materialized if used multiple times or explicitly forced with `WITH cte AS MATERIALIZED (...)`.
Materialization can be a problem because it prevents the optimizer from pushing constraints (like `WHERE` filters) from the outer query down into the CTE. This can result in the database scanning and computing large amounts of data inside the CTE, only to immediately throw most of it away when applying outer filters.

## 11. Write a query using a scalar subquery in the SELECT clause to add the department's average salary next to each employee's salary.
```sql
SELECT 
    e.emp_id, 
    e.name, 
    e.salary,
    (SELECT AVG(salary) 
     FROM employees d 
     WHERE d.dept_id = e.dept_id) AS dept_avg_salary
FROM employees e;
```

## 12. How would you refactor a correlated subquery into a JOIN or window function?
Correlated subqueries often recalculate aggregates row-by-row. By using window functions, the database can calculate the aggregate over a partitioned set during a single pass.
*Before (Correlated Subquery):*
`SELECT name, salary, (SELECT MAX(salary) FROM employees e2 WHERE e2.dept_id = e1.dept_id) FROM employees e1;`
*After (Window Function):*
```sql
SELECT 
    name, 
    salary,
    MAX(salary) OVER (PARTITION BY dept_id) AS dept_max_salary
FROM employees;
```

## 13. What is the maximum recursion depth in common SQL databases and how do you control it?
Most databases do not have a hardcoded syntax limit for recursion depth, but they are limited by configuration or memory. 
- In PostgreSQL, you can use the `STATEMENT_TIMEOUT` setting, or logically prevent infinite recursion using cycle detection logic or depth counters within the recursive CTE itself (e.g., `WHERE level < 100`).
- SQL Server limits recursion to 100 by default, which can be overridden using `OPTION (MAXRECURSION n)` at the end of the query.

## 14. Write a CTE that calculates month-over-month revenue and flags months with negative growth.
```sql
WITH monthly_revenue AS (
    SELECT 
        DATE_TRUNC('month', order_date) AS order_month,
        SUM(amount) AS revenue
    FROM orders
    GROUP BY DATE_TRUNC('month', order_date)
),
revenue_growth AS (
    SELECT 
        order_month,
        revenue,
        LAG(revenue) OVER (ORDER BY order_month) AS prev_month_revenue,
        revenue - LAG(revenue) OVER (ORDER BY order_month) AS revenue_diff
    FROM monthly_revenue
)
SELECT 
    order_month, 
    revenue, 
    revenue_diff,
    CASE WHEN revenue_diff < 0 THEN TRUE ELSE FALSE END AS negative_growth_flag
FROM revenue_growth;
```

## 15. What is the difference between UNION and UNION ALL? When should you prefer UNION ALL?
`UNION` combines the result sets of two queries and automatically removes duplicate rows. This deduplication requires a costly sort or hash operation.
`UNION ALL` combines result sets but retains duplicates, executing much faster since it bypasses the deduplication step.
You should strictly prefer `UNION ALL` unless you specifically require duplicate rows to be removed, as the performance penalty of `UNION` is significant on large datasets. In Recursive CTEs, `UNION ALL` is heavily standard to bridge the anchor and recursive components.
