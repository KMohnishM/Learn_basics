# Module 5: Memory Management

---

## 1. Why Memory Management?

The CPU can only directly execute instructions stored in main memory (RAM). Programs must be loaded into RAM before they can run. Memory management is the OS subsystem that handles:
- **Allocation**: Giving each process its portion of memory.
- **Protection**: Preventing processes from accessing each other's memory.
- **Translation**: Converting addresses from process's perspective to physical RAM locations.
- **Sharing**: Allowing controlled sharing of code (shared libraries) across processes.

---

## 2. Logical vs Physical Address Space

**Logical address** (virtual address): The address generated by the CPU — what the program "thinks" the address is. Starts at 0 for every process.

**Physical address**: The actual location in RAM. The OS manages which physical frame a logical page maps to.

**Memory Management Unit (MMU)**: Hardware component that translates logical to physical addresses on every memory access. The CPU sends a logical address → MMU outputs a physical address → RAM is accessed.

**Why the distinction matters**: Multiple processes each think they have addresses starting at 0. The MMU ensures they're transparently mapped to different physical locations, providing isolation.

---

## 3. Address Binding — When Addresses Are Assigned

**Compile-time binding**: The compiler generates absolute addresses (assumes the program will be loaded at a specific memory location). Problem: The program must always be loaded at that exact address. Inflexible.

**Load-time binding**: The compiler generates relocatable code (relative addresses). At load time, the loader converts them to absolute addresses based on where in memory the program is loaded. Once loaded, addresses are fixed.

**Execution-time binding** (runtime relocation): Addresses are not resolved until the instruction actually executes. The CPU uses base + offset to compute the physical address at runtime. **Required for virtual memory systems** — the process can be moved in memory without changes, because addresses are computed fresh on each access.

Most modern systems use **execution-time binding** via the MMU's relocation register (base register).

---

## 4. The Simple MMU — Base + Limit Registers

The simplest form of hardware address translation: two registers per process.

- **Base register**: Physical starting address of the process's memory region.
- **Limit register**: Length (size) of the process's memory region.

**Address translation:**
```
Physical address = Logical address + Base register

Validity check:
If Logical address >= Limit register:
    → Protection fault (SIGSEGV — segmentation violation)
```

**Protection**: Each memory access is checked. A process cannot access memory below its base or above base+limit.

**Problem**: The process must occupy a contiguous region of physical memory. This leads to fragmentation issues (see Section 7).

---

## 5. Dynamic Loading and Dynamic Linking

**Dynamic Loading**: A program's routines are not loaded until they are called. The entire program image is on disk; only the called portions are loaded into memory on demand.

Advantage: If a large program has error-handling routines that are rarely called, they're never loaded in typical execution. Reduces memory footprint.

**Dynamic Linking**: Linking (connecting function calls to function code) is deferred until runtime. The executable contains "stubs" (small pieces of code). When a stub is first executed, it finds the library in memory (or loads it), then overwrites itself with the real address.

**Shared libraries** (`.so` on Linux, `.dll` on Windows): One copy of the library code in physical memory, shared by all processes that use it. Essential — if all 100 running processes each had a private copy of libc, that would waste gigabytes of RAM for identical code.

**Position-Independent Code (PIC)**: Shared library code compiled so it works regardless of where in virtual memory it's loaded. Uses relative addressing — no absolute addresses that would differ per process.

---

## 6. Contiguous Memory Allocation

Early approach: each process gets one contiguous block of physical memory.

### Fixed Partitioning

RAM is divided into fixed-size partitions at boot time. Each partition gets exactly one process.

**Internal Fragmentation**: When a process is smaller than the partition assigned to it, the remaining space in that partition is wasted. Example: 64KB partition, 25KB process → 39KB wasted (internal, inside the partition).

### Variable Partitioning

Partitions created dynamically, exactly the size of each process.

When a process exits, it leaves a "hole" in memory. Over time, multiple holes appear at non-contiguous locations.

**External Fragmentation**: Total free memory is sufficient to satisfy a request, but it's scattered in non-contiguous pieces. No single hole is large enough. Example: 30KB process needs space. 10KB hole + 10KB hole + 10KB hole = 30KB total free, but no single 30KB block.

### Hole Allocation Strategies

Given a process of size n and multiple holes:

**First Fit**: Allocate the first hole that is large enough. Fast. Can leave large holes available at the end.

**Best Fit**: Allocate the smallest hole that is large enough. Leaves smallest leftover hole. Searches entire list. Produces many tiny useless fragments.

**Worst Fit**: Allocate the largest hole. Leaves largest remaining hole. Performs poorly in practice.

**Result**: Studies show First Fit and Best Fit are both better than Worst Fit. First Fit is generally faster. Neither is clearly superior for fragmentation.

**50% Rule**: Statistical result for First Fit. Given N allocated blocks, approximately 0.5N blocks are lost to fragmentation. For every 2 usable blocks, 1 block is wasted.

---

## 7. Compaction — Fighting External Fragmentation

Move all processes to one end of memory, consolidating all free space into one large block. Like defragmenting a hard drive.

**Cost**: Must relocate every process — relocate all pointers, update page tables. Very expensive (potentially copying gigabytes of data). Only possible with runtime binding (execution-time address resolution).

**Not practical for most OSes** — paging (see next section) solves external fragmentation without compaction.

---

## 8. Paging — The Foundation of Modern Memory Management

**Key insight**: Why does a process need to occupy contiguous physical memory? It doesn't — we just need the CPU to think it does.

**Paging** divides both logical and physical memory into equal fixed-size blocks:
- **Page**: Fixed-size block of logical memory (typical size: 4KB)
- **Frame**: Fixed-size block of physical memory (same size as a page)

A process's logical pages can be stored in ANY available physical frames — no contiguity requirement.

**No external fragmentation**: Any free frame can hold any page.
**Internal fragmentation**: Only in the last page of each process (average: half a page per process = 2KB wasted for 4KB pages).

### Address Structure

A logical address has two parts:

```
[ Page Number (p) | Page Offset (d) ]
     ←  upper bits  →  ← lower bits →
```

For 32-bit address space with 4KB pages:
- Page size = 4KB = 2^12 bytes → offset = 12 bits
- Page number = 32 - 12 = 20 bits → up to 2^20 = 1M pages

**Address translation:**
```
Physical address = Frame(p) × PageSize + d
```

Where `Frame(p)` is looked up in the **page table**.

### Page Table

A per-process data structure stored in the kernel. Maps page numbers to frame numbers.

```
Page Table for Process A:
  Page 0 → Frame 5
  Page 1 → Frame 3
  Page 2 → Frame 8
  Page 3 → Frame 7

Address 0x1234 = page 1, offset 0x234
Frame 3, physical = 3×4096 + 0x234 = 12288 + 564 = 12852
```

### Page Table Entry (PTE) Fields

Each entry contains more than just the frame number:

| Field | Bits | Purpose |
|-------|------|---------|
| **Frame Number** | 20+ | Physical frame for this page |
| **Valid/Invalid** | 1 | 0 = page not in memory (page fault) |
| **Protection** | 2–3 | Read/Write/Execute permissions |
| **Dirty (Modified)** | 1 | 1 = page has been written (must write back if swapped out) |
| **Referenced (Accessed)** | 1 | 1 = page recently used (for page replacement) |
| **Caching Disabled** | 1 | For device registers — don't cache |

### The Two-Memory-Access Problem

For each memory access, the CPU must:
1. Read the page table (1 memory access) → get frame number
2. Access actual data at physical address (1 memory access)

Every memory access now costs **2 memory accesses**. This halves effective memory speed! This is solved by the TLB.

---

## 9. TLB — Translation Lookaside Buffer

A small, fast hardware cache inside the MMU that stores recent page number → frame number translations.

**Typical TLB size**: 64 to 1024 entries (very small, but the 80/20 rule applies: most accesses hit a small number of pages).

**Access pattern:**
```
CPU generates logical address [page p, offset d]
    ↓
TLB lookup (parallel search of all entries, ~1 nanosecond):
    HIT  → Frame f from TLB, physical = f × PageSize + d, 1 memory access total
    MISS → Access page table (1 memory access), update TLB, then access data (1 more)
```

**Effective Access Time (EAT):**
```
EAT = h × (t_TLB + t_mem) + (1 - h) × (t_TLB + 2×t_mem)

Where:
  h = TLB hit ratio (typically 0.90 to 0.99)
  t_TLB = TLB access time (e.g., 20ns)
  t_mem = memory access time (e.g., 100ns)

Example (h=0.90, t_TLB=20ns, t_mem=100ns):
EAT = 0.90×(20+100) + 0.10×(20+200)
    = 0.90×120 + 0.10×220
    = 108 + 22 = 130ns

Slowdown vs no paging = 130/100 = 1.30 (only 30% overhead with 90% hit rate)
```

**TLB on context switch**: A TLB entry is only valid for the current process (each process has its own page table). On context switch:
- **Simple approach**: Flush the entire TLB (invalidate all entries). Next process starts cold, incurring TLB misses until refilled.
- **ASID (Address Space Identifier)**: Each TLB entry tagged with the process's ASID. No flush needed — TLB entries from different processes coexist, identified by ASID. Supported by most modern CPUs (ARM, x86 via PCID on recent CPUs).

---

## 10. Hierarchical (Multi-Level) Page Tables

**Problem**: A 32-bit process has a 4GB virtual address space with 4KB pages → 1 million pages → page table needs 1M × 4 bytes = **4MB per process**. With 100 processes, that's 400MB just for page tables. And the page table must be contiguous in physical memory.

**Solution**: Page the page table itself — multi-level paging.

### Two-Level Page Table (32-bit)

Split the 20-bit page number into two parts:
```
[ 10-bit outer index | 10-bit inner index | 12-bit offset ]
```

- **Outer page table**: 2^10 = 1024 entries (4KB — fits in one frame!)
- **Inner page table**: Created only for regions of virtual memory that are actually used.

If a process uses only a small portion of its 4GB space (typical for most processes), most inner page table entries are null — not created. Only used portions of the virtual space require inner tables.

**Trade-off**: For a fully-used 32-bit process, two-level paging uses MORE memory (1 outer table + 1024 inner tables = 1025 × 4KB = 4.1MB vs 4MB flat). But for sparse address spaces, it's much more efficient.

### 64-Bit Systems

32-bit processors: 2-level page tables work.
64-bit processors: 4 or 5 levels of page tables needed. Linux on x86-64 uses 4-level page tables (PGD → PUD → PMD → PTE). The upper bits of a 64-bit address are often unused (current CPUs only support 48 actual address bits → 256TB virtual space per process).

### Hashed Page Tables

For very sparse 64-bit address spaces: maintain a hash table with page number as key. Hash collisions handled via chaining.

### Inverted Page Table

Instead of per-process page tables (mapping logical → physical), one global table with one entry per **physical frame** (mapping physical → logical owner).

- Single table for the whole system → constant memory overhead regardless of number of processes
- Finding the frame for a logical address requires searching the entire table → slow (O(n))
- Fix: Hash the logical address first to narrow the search
- Used by IBM RISC, some PowerPC systems, and conceptually by some ARM processors

## 11. Segmentation

**Paging** divides memory mechanically into fixed-size pages (no regard for program structure).

**Segmentation** divides memory according to the logical structure of the program. A program consists of naturally-distinct segments:
- Code segment (text)
- Global data segment
- Stack segment
- Heap segment
- Shared library segment

Each segment has a name (number) and a length. Addresses are `(segment_number, offset)`.

**Segment Table**: Each entry has:
- **Base**: Starting physical address of this segment
- **Limit**: Length of this segment (offset must be < limit)

**Advantages:**
- Natural sharing: Two processes can share a code segment at different virtual addresses.
- Natural protection: Code segment can be marked read-only; data segment writable.
- Segments can grow/shrink independently (heap grows, stack grows, neither affects the other).

**Disadvantage**: **External fragmentation** — segments are variable-size, so holes in memory form over time (same problem as variable-partition allocation). This is why pure segmentation is rarely used today.

---

## 12. Segmentation + Paging (Intel x86)

Real CPUs often combine both:
1. The logical address → segment base address (via segment table)
2. The segment-relative address → physical address (via page table)

Intel x86 in protected mode: segments select a region; paging then manages that region. The GDT (Global Descriptor Table) contains segment descriptors. Linux simplifies this by making all segments cover the full 4GB address space (effectively ignoring segmentation), relying purely on paging.

---

## 13. Shared Pages

With paging, sharing is straightforward: Two processes' page tables can point to the same physical frame.

**Requirement**: Shared code must be **reentrant** (pure code, no self-modifying code, no process-specific data). Read-only code automatically satisfies this.

**Example**: 40 users each running the same editor (e.g., `vi`). The editor binary is 150KB. Without sharing: 40 × 150KB = 6MB for code. With shared pages: 150KB (one copy) + 40 × (private data pages). Massive saving.

Shared libraries (libc, libpthread) work the same way — one physical copy, mapped into each process's virtual space at potentially different virtual addresses.
