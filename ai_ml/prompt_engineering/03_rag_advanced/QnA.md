# Advanced RAG - Questions and Answers

### 1. Why does naive fixed-size chunking frequently cause retrieval failures in production RAG systems? Explain semantic chunking.
Naive fixed-size chunking splits documents rigidly based on character or token counts (e.g., every 500 tokens). This mechanical splitting frequently bisects complete sentences, paragraphs, or related thoughts, causing critical context to be orphaned in separate chunks. When the LLM retrieves these fragmented chunks, it struggles to construct a coherent and factually accurate response because the underlying logic or connecting details are missing. 
Semantic chunking solves this by determining boundaries dynamically based on meaning rather than math. It embeds individual sentences and compares the cosine similarity of adjacent sentences. As long as adjacent sentences remain highly similar (above a predefined threshold), they are grouped into the same chunk. When the similarity drops—indicating a shift in topic or idea—a new chunk is created. This ensures that the retrieved blocks of text contain complete, unified concepts, drastically improving the LLM's synthesis quality and reducing hallucinations in production.

### 2. Explain the Parent-Document (Hierarchical) chunking strategy. How does it resolve the tension between small retrieval chunks and large LLM context needs?
In RAG systems, there is an inherent tension: small chunks yield the most precise, accurate search results during vector similarity matching, but large chunks provide the comprehensive context an LLM needs to synthesize a high-quality answer. Parent-Document (or Hierarchical) chunking elegantly resolves this paradox. 
The system first splits a document into large "parent" chunks (e.g., 2000 tokens) and then further subdivides those parents into smaller "child" chunks (e.g., 200 tokens). Only the embeddings of the small child chunks are stored and searched in the vector database. However, each child chunk retains a metadata link back to its specific parent chunk. When a user query closely matches a child chunk, the retrieval engine does not return just the child; instead, it fetches and feeds the entire parent chunk to the LLM. This provides the best of both worlds: laser-focused search precision at the child level, combined with the expansive, rich context of the parent level for generation.

### 3. What is Hypothetical Document Embeddings (HyDE)? Walk through the step-by-step lifecycle of a HyDE query.
Hypothetical Document Embeddings (HyDE) is an advanced query transformation technique designed to bridge the semantic gap between short user queries and long, detailed informational documents. Users often ask brief questions (e.g., "What is the capital of France?"), whereas the target document might be a long encyclopedia entry. 
The lifecycle begins when the user submits a query. First, the query is routed to an LLM with a zero-shot prompt instructing it to generate a hypothetical, detailed answer to the query. This generated document is "hallucinated" and may contain factual inaccuracies, but structurally and semantically, it looks exactly like the target document the system hopes to find. Next, this hallucinated hypothetical document is embedded into a dense vector by the embedding model. Finally, this vector is used to perform the similarity search against the vector database. Because the vector represents a full, descriptive paragraph rather than a terse question, it naturally aligns closer to the actual relevant documents in the embedding space, significantly boosting retrieval accuracy and recall.

### 4. How does Anthropic's Contextual Retrieval technique improve retrieval accuracy by prepending document-level context to individual chunks?
Standard chunking methodologies inherently destroy document-level context. For example, a chunk might state "The Q3 revenue increased by 45%," but because it was extracted from page 40 of a financial report, it lacks the company name and the specific year. If a user queries "ACME Corp 2023 Q3 revenue," this chunk might not be retrieved due to low semantic overlap.
Anthropic's Contextual Retrieval directly addresses this by leveraging an LLM during the ingestion phase. Before embedding, the original full document and the specific extracted chunk are passed to an LLM. The LLM is prompted to write a very brief (1-2 sentence) summary situating the chunk within the broader document—for instance, "This chunk discusses ACME Corp's financial performance in Q3 2023." This generated context is then physically prepended to the chunk text. The combined text (Context + Chunk) is then embedded and stored. This ensures every single chunk carries the global context of its source material, leading to massive improvements in retrieval precision for highly specific queries.

### 5. What is Late Chunking, and how does it preserve cross-chunk semantic context compared to standard early chunking?
Standard "early chunking" involves splitting a document into strings of text and then passing each string independently through an embedding model (like a BERT or transformer encoder). Because each chunk is processed in isolation, the transformer's attention mechanism cannot see the rest of the document, resulting in embeddings that lack broader context.
Late Chunking reverses this pipeline. The entire document (or a very large segment of it) is passed through the transformer model in a single pass. The self-attention layers allow every token to interact with every other token in the document, deeply enriching the contextual representation of each word. Only after these contextualized token embeddings are generated does the system apply the chunk boundaries. The token embeddings within each predefined boundary are then pooled (e.g., average pooling) to create the final chunk embedding. Consequently, the resulting chunk embeddings inherently encode the semantic flavor of the surrounding text, leading to vastly superior retrieval performance without the need for secondary LLM context generation.

### 6. Compare Dense Vector Search and Sparse BM25 Search. Give concrete examples where dense search fails and sparse search succeeds, and vice versa.
Dense Vector Search relies on transformer-based embedding models to map text into a continuous semantic space. It matches concepts and meanings rather than exact words. It excels at semantic queries, such as retrieving a document about "dogs" when the user queries "canines." However, dense search frequently fails on out-of-vocabulary terms, specific product IDs, or exact names because these strings don't map neatly to general semantic concepts.
Sparse BM25 Search is a classic keyword-based lexical algorithm relying on Term Frequency-Inverse Document Frequency (TF-IDF). It excels at finding exact matches. If a user searches for error code "ERR-90210-X," BM25 will perfectly locate the exact document containing that string, whereas dense search might return generic error logs. Conversely, BM25 completely fails if the query uses synonyms; a search for "automobile" will yield zero results if the document only uses the word "car." Hybrid search combines both approaches to mitigate their respective weaknesses.

### 7. Explain the Reciprocal Rank Fusion (RRF) formula. How does it merge ranked lists from disparate retrieval algorithms without score normalization issues?
When implementing hybrid search, you obtain two ranked lists: one from a dense vector search (with cosine similarity scores like 0.89) and one from a sparse BM25 search (with unbounded lexical scores like 15.4). Because these scores exist on entirely different mathematical scales and distributions, they cannot be simply added or averaged to determine a final ranking.
Reciprocal Rank Fusion (RRF) resolves this by completely ignoring the raw scores and focusing exclusively on the document's rank position within each list. The formula is: RRF_Score = 1 / (k + Rank), where 'k' is a smoothing constant (typically set to 60) and Rank is the position (1, 2, 3...) of the document in the list. To merge the lists, the algorithm calculates the RRF score for a document in the dense list and adds it to the RRF score for the same document in the sparse list. This creates a fair, normalized consensus ranking that heavily rewards documents that appear near the top of both lists, robustly integrating semantic and lexical signals.

### 8. What is the difference between a Bi-Encoder and a Cross-Encoder? Why are Cross-Encoders used exclusively for reranking rather than initial search?
A Bi-Encoder processes two pieces of text (e.g., a query and a document) entirely independently. The query goes through the model to produce a vector, and the document goes through the model to produce a vector. Their similarity is then calculated using a simple, fast dot-product or cosine similarity. Because document embeddings can be pre-computed and indexed, Bi-Encoders are incredibly fast and scale to millions of documents.
A Cross-Encoder, however, concatenates the query and the document together (e.g., "[CLS] Query [SEP] Document [SEP]") and passes them simultaneously through the transformer's attention layers. This allows the model to deeply compare the words in the query directly against the words in the document, resulting in a highly accurate relevance score. However, this joint processing is computationally explosive; it cannot be pre-computed. Running a Cross-Encoder against a million documents for every query would take hours. Thus, Cross-Encoders are used strictly as a second-stage "reranker" to precisely re-evaluate only the top 50 to 100 candidates retrieved by the fast Bi-Encoder.

### 9. Describe the Self-RAG architecture. How do reflection tokens enable an LLM to evaluate retrieval necessity and factual groundedness?
Self-RAG (Self-Reflective Retrieval-Augmented Generation) is an advanced paradigm where the language model is explicitly trained to govern its own retrieval and generation process. Instead of blindly accepting retrieved context, a Self-RAG model generates special structural "reflection tokens" during inference to dictate the pipeline's behavior dynamically.
As the LLM processes a prompt, it may output a `[Retrieve]` token if it realizes it lacks internal knowledge. This pauses generation, triggers the external vector database search, and appends the results to the context. The LLM then generates text based on the documents, subsequently outputting a `[Relevant]` token to indicate if the fetched document was actually useful. Furthermore, it outputs a `[Fully Supported]` or `[Partially Supported]` token to grade whether the sentence it just generated is rigorously grounded in the retrieved facts. This self-critique mechanism drastically reduces hallucination, as the model explicitly verifies its own output against the retrieved evidence in real-time.

### 10. What is Corrective RAG (CRAG)? What corrective actions are triggered when the retrieval evaluator scores a document set as incorrect or ambiguous?
Corrective RAG (CRAG) introduces a deterministic retrieval evaluator into the standard RAG pipeline to assess the quality of retrieved documents before generation occurs. When the vector database returns a set of documents, a lightweight evaluator (often a smaller, fine-tuned LLM or a specific prompt) grades the relevance of the documents to the query, outputting a strict classification: Correct, Incorrect, or Ambiguous.
If the retrieval is deemed "Correct," the pipeline proceeds normally to the main generation LLM. If "Incorrect," CRAG triggers a robust corrective action: it completely discards the vector database results and pivots to an external web search API (like Tavily or Bing) to scrape live data, assuming the internal knowledge base lacks the answer. If the evaluation is "Ambiguous," the system performs query rewriting and reformulation, running both a broader vector search and a targeted web search to stitch together sufficient context. This conditional logic acts as a powerful safety net against poor retrieval.

### 11. How does Multi-Query Expansion work, and how does it overcome vocabulary mismatch in user queries?
Users often formulate queries using terse, ambiguous language or specific terminology that does not match the vocabulary used in the source documents. For example, a user might search for "fix PC screen glitch," while the technical manual refers to "resolving display artifacting." This vocabulary mismatch causes standard vector retrieval to fail.
Multi-Query Expansion tackles this by using an LLM to rewrite the original user query into multiple, distinct variations before performing the search. Given the original query, the LLM is prompted to generate 3 to 5 alternative queries from different perspectives, using synonyms, technical jargon, and layperson terms. Each of these variations is embedded and used to search the vector database in parallel. The results from all queries are then pooled, deduplicated, and passed to the generation phase. By casting a wider, multi-faceted semantic net, Multi-Query Expansion easily bypasses vocabulary mismatches and significantly increases the recall of relevant documents.

### 12. What strategies prevent context stuffing (overwhelming the LLM with 20 retrieved documents) from degrading response quality?
While modern LLMs boast massive context windows (up to 1 million tokens), feeding them dozens of retrieved documents—known as context stuffing—often degrades performance. LLMs suffer from the "Lost in the Middle" phenomenon, where they heavily weight information at the very beginning and very end of the prompt but ignore facts buried in the center. Furthermore, excess irrelevant information dilutes the model's focus, increasing the likelihood of hallucinations.
To prevent this, practitioners implement strict two-stage reranking to narrow down the context to only the top 3 to 5 most critically relevant documents. Additionally, techniques like "Document Summarization" can be applied, where an intermediate LLM summarizes each retrieved document before concatenating them into the final prompt. Prompt engineering techniques, such as explicitly instructing the model to cite specific chunks or XML tags (e.g., `<doc1>`, `<doc2>`), help force the attention mechanism to accurately map the retrieved context to the generated answer without getting overwhelmed by noise.

### 13. How should tables and semi-structured data (CSV, Markdown tables) be parsed, indexed, and retrieved in RAG pipelines?
Standard RAG pipelines treat all text as flat strings, which is disastrous for tabular data. Flattening a CSV or Markdown table into a string destroys the row-column spatial relationships, making it impossible for the embedding model to understand that "Revenue" in column 2 corresponds to "2023" in column 1.
To handle tabular data correctly, advanced RAG architectures bypass standard text embedding. One highly effective strategy is Table Summarization: an LLM is used during ingestion to generate a descriptive, natural language summary of the table's purpose and contents. This summary is embedded and indexed. When retrieved, the actual raw table (in CSV, JSON, or HTML format) is passed to the generation LLM, allowing it to read the exact structure. Alternatively, for large datasets, the system can use Text-to-SQL or Pandas DataFrame agents. In this approach, the user's query is routed to a specialized agent that writes and executes SQL or Python code against the tabular data, extracting the exact answer deterministically rather than relying on vector similarity.

### 14. What are the key metrics for measuring retrieval performance (e.g., Hit Rate@K, MRR@K, NDCG@K)?
Evaluating the generation phase of RAG is subjective, but evaluating the retrieval phase requires rigorous, mathematical metrics. Hit Rate @ K measures the binary success of the retrieval; it calculates the percentage of queries where at least one truly relevant document appeared in the top K results. It is simple but doesn't account for the document's position within those top K.
Mean Reciprocal Rank (MRR @ K) addresses ranking. It finds the rank of the first relevant document retrieved and takes its reciprocal (1/rank). A relevant document at rank 1 scores 1.0, while rank 4 scores 0.25. The MRR is the average of these scores across all queries, heavily penalizing systems that bury the correct answer. Normalized Discounted Cumulative Gain (NDCG @ K) is the most comprehensive metric. It handles scenarios where multiple documents are relevant, and where some documents are more relevant than others (graded relevance). NDCG applies a logarithmic discount to documents lower in the ranking, ensuring that the system is optimized to push the most highly relevant documents to the absolute top of the list.

### 15. How do you implement metadata filtering in vector databases to enforce tenant isolation and role-based access control (RBAC) in enterprise RAG?
In enterprise environments, data security is paramount. A single vector database often houses documents belonging to multiple clients (multi-tenancy) or different departments with strict confidentiality rules (e.g., HR vs. Engineering). Relying on the LLM to ignore sensitive data is a critical security vulnerability; the data must be physically blocked at the database level using Role-Based Access Control (RBAC).
This is achieved through metadata filtering. During ingestion, every document chunk is tagged with precise metadata (e.g., `{"tenant_id": "client_A", "clearance_level": "secret"}`). When a user queries the system, the application backend determines the user's identity and privileges. It then constructs a hard filter (a pre-filter) and attaches it to the vector search query. The vector database evaluates this filter before computing cosine similarities, physically excluding any vectors that do not match the authorized metadata. Pre-filtering guarantees that exactly K results are returned from the authorized subset, ensuring strict cryptographic-like isolation of data while maintaining optimal search performance.
